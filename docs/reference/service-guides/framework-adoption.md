# Adopt Jafly in an OpenPlatform service

A framework upgrade changes shared infrastructure, while each service retains its business rules, transaction boundaries, identity requirements and SDK contracts. Qualify the effective dependency graph, compiled code, packaged application and actual customer operation separately. A successful parent build does not rebuild its consumers.

## Choose coherent parent and BOM inputs

OpenPlatform services inherit `io.fireflysoftware:firefly-parent`. That parent extends `org.fireflyframework:fireflyframework-parent` and imports `fireflyframework-bom` through `fireflyframework.bom.version`. The platform BOM separately selects OpenPlatform artifacts. Keep the framework parent and BOM aligned centrally; an individual service should not silently override one framework module with another train.

The current repository working parent is OpenPlatform `26.10.6` with Jafly `26.10.22`. This is a source qualification train, not a statement that those framework changes have been published. Use the reviewed source/artifacts in an isolated development repository until an actual release is available. Never replace artifacts in a shared deployment cache under an unchanged coordinate and assume deployed applications changed.

Read the service's effective parent and its actual framework graph from its root:

```sh
mvn -B help:effective-pom -Doutput=effective-pom.xml
mvn -B dependency:tree -Dincludes=org.fireflyframework
```

Check every resolved framework coordinate, including transitive SDK dependencies and test/runtime scopes. An effective property shows intended selection; it does not establish which bytes an existing application contains. Use the JDK required by the selected parent and supply repository credentials through the deployment's Maven settings/environment, never source files.

## Build from clean source inputs

Use a new isolated source checkout or source snapshot with no inherited `target` directories. Preserve the service's source baseline, reviewed local changes, parent/BOM identity and input specification. An old generated API class can remain in a target directory after genuine generation no longer emits it. An incremental executable can also retain an older dependency even after dependency resolution changes.

Run the repository's configured checks. For services using the shared OpenAPI producer lifecycle, a normal verification is:

```sh
mvn -B verify
```

That lifecycle can start the producer temporarily to obtain its real API contract. Coordinate the configured generation port when several repositories run concurrently. A fresh `-DskipOpenApiGen verify` may be used for a source/regression check against an already reviewed unchanged specification; it does not regenerate the producer contract. Keep SDK generation from that specification enabled. A generated client with no classes is not successful client qualification.

Review test setup before execution. Database tests must use a private disposable database and matching JDBC/R2DBC configuration. Provider fixtures must bind to owned loopback endpoints or explicitly selected sandboxes. A hostname containing `localhost` does not establish test ownership. Supply required fixture properties explicitly and report disabled or skipped cases; do not interpret zero executed tests as business validation.

## Inspect the packaged application

Compare embedded framework and internal SDK JAR hashes with the exact reviewed inputs. For an executable Spring Boot JAR, this inspection prints its embedded framework identities:

```sh
python3 - "$APPLICATION_JAR" <<'PY'
import hashlib
import sys
import zipfile

with zipfile.ZipFile(sys.argv[1]) as application:
    entries = [name for name in application.namelist()
               if name.startswith("BOOT-INF/lib/fireflyframework-") and name.endswith(".jar")]
    if not entries:
        raise SystemExit("No embedded framework JARs found; inspect this packaging format explicitly")
    for name in sorted(entries):
        print(hashlib.sha256(application.read(name)).hexdigest(), name)
PY
```

Set `APPLICATION_JAR` to the actual newly produced executable. Compare those values with the approved artifact manifest rather than a mutable sibling target directory. Inspect the embedded service modules and SDKs as well. Record an artifact mismatch as a packaging failure and rebuild from fresh inputs before runtime qualification.

## Preserve public SDK compatibility deliberately

Generate a producer's SDK from the actual producer contract. Compare operation routes, verbs, parameters, required fields, response codes and model schemas. Also compare public Java signatures: wire compatibility alone does not preserve a renamed generated API class or a changed optional-header argument.

Keep SDK production code generated by the repository's existing OpenAPI Generator configuration. Do not add handwritten client classes, compatibility subclasses, model copies, patched generated output, custom transport wrappers, or post-generation edits inside the SDK. Preserve established API class and method names through the producer's tags and explicit operation IDs. Express request, response, required-field, parameter and security contracts in the owning producer's controllers and DTOs, then regenerate the specification and client. If an intentional breaking change is necessary, version the contract and migrate its consumers explicitly.

For code-first services, use this source flow:

1. Change the owning controller/DTO and its OpenAPI annotations. Keep trusted runtime principals hidden from public parameters; declare the actual bearer scheme rather than exposing authentication objects as request inputs.
2. Run the normal producer lifecycle and obtain the service's real OpenAPI document. Review both wire shapes and generated Java signatures. A saved YAML used with `-DskipOpenApiGen` alone cannot establish that the producer still emits that contract.
3. Generate APIs, models and invoker support with the existing Maven plugin, library and package configuration. Start from a fresh build directory so obsolete classes cannot survive regeneration. Never disable client generation to make compilation pass.
4. Exercise the newly packaged SDK over HTTP: paths, verbs, headers, body serialization, list/optional/null responses, laziness and error propagation. Include the declared authentication mechanism and current authorization denial where the operation requires it.
5. Rebuild direct consumers and inspect the exact SDK JAR embedded in each new executable. Keep generated-contract compatibility distinct from the business correctness of the called operation.

`useTags` and `operationId` are public Java API inputs. A controller rename must not silently rename a supported generated class. Optional headers may keep the same Java argument while changing validation behavior; verify both the signature and the actual missing-header request. For nullable models, use the generated invoker's configured mapper and nullable module. Validate the OpenAPI version actually emitted: a 3.0 `nullable` attribute and a 3.1 null union express different schema syntax.

An application adapter may implement a domain/core port and call a generated SDK from its existing infrastructure package. That adapter owns business-to-client mapping and provider configuration; it must not recreate the SDK's wire implementation or add authored production Java to the SDK module. Keep adapter lifecycle/reconciliation tests separate from generator-provenance checks.

An SDK available in the build cache is not proof that its owning service has been rebuilt or that a downstream experience uses it. Qualify each direct consumer and its exact packaged SDK separately.

## Check behavior at framework boundaries

| Boundary | Service responsibility during adoption |
| --- | --- |
| CQRS queries | Default cache keys are absent. A deliberate key must include every result-affecting input and trusted authority scope; current-state handlers should disable caching. Test different resource/tenant requests and current denied access. |
| HTTP replay | Retain stable business action IDs and exact intent. Operations requiring current resource authority must not reuse an old successful transport response instead of evaluating current policy. |
| R2DBC | Configure the actual database and intended transaction manager. Optional infrastructure must back off in database-free applications; multiple factories need deliberate selection. |
| Filter DTOs | Special NULL/NOT_NULL markers belong to the exact DTO instance. A different equal object or changed hash cannot exchange or lose markers. Check actual query results and runtime OpenAPI for typed parameter objects. |
| OAuth service clients | Configure actual registrations, scopes and credentials. Test native client acquisition and project SPI replacement; absence or failure cannot create a synthetic service identity. |
| gRPC | Align the generator's framework property with every resolved gRPC runtime artifact. Inspect native compiler architecture and exercise a generated client over an owned transport; a mixed Netty/core train can compile and fail at startup. |
| JWT/resource policy | Require signature validation, issuer, audience and expiration, then validate current tenant/resource authority. Generic principal conversion does not automatically preserve every product-specific signed attribute or the original token. |
| Saga/TCC | Preserve native effect/action identities and owner status lookup. If REQUIRED TCC persistence acknowledgments are selected, success follows the final acknowledgment; uncertainty requires reconciliation. |
| Documents | Preserve exact schema/facts strings and numbers through SDKs. Shared validation/rendering mechanisms do not establish template authority, issuer approval or authoritative financial facts. |
| Errors | Retain business correlation/recovery metadata while keeping internal diagnostics out of ordinary production responses. |

A default SPI implementation must back off to a plain project bean without configuration-order dependence, duplicate authorities, bean overriding or an unexplained `@Primary` requirement. Test both registration orders, ordinary application scanning, default-disabled startup and the enabled runtime. Use supported Boot auto-configuration ordering for infrastructure defaults where appropriate; a conditional bean inside an ordinary scanned configuration can be evaluated too early.

Do not persist bearer tokens, OAuth secrets or caller authority in saga/business journals. Acquire current credentials and policy decisions at the intended operation boundaries. Mutable global SDK headers cannot safely represent concurrent callers; use invocation-scoped clients or the service's explicitly supported credential mechanism.

## Run the customer journey

Start the reviewed experience, domain and owning core executables with genuine SDKs and private migrated owner stores. Establish synthetic identities through an explicitly selected trusted fixture and create actual business records through their owner APIs. Read returned identifiers and parent/tenant associations; do not replace missing owner data with guessed UUIDs or favorable sample results.

Verify normal completion, current denial, stale/changed intent, missing owner observations, unavailable adapters, ambiguous external outcomes, lost responses, process restart and concurrent requests. For payments, verify authoritative booked/held/available amounts and retained effect identities. For insurance, preserve quotation/referral/binding/coverage/premium/claim distinctions. For documents, verify actual retained content, exact source facts and the native attachment/signature/delivery state relevant to the operation.

A sandbox demonstrates its implemented contract only. Replacing it with a live adapter requires the same supported lifecycle, idempotency, callback, reconciliation and error semantics plus separate provider qualification.

## Document and release

Update the source-owned service guide, configuration examples, adapter replacement/recovery instructions and banner-preserving README. Refresh public API and guide snapshots from their owning sources; do not invent a YAML contract or copy internal execution registers into the platform manual.

Retain source/artifact identities, commands, fresh test reports and runtime evidence. Distinguish source qualification, consumer adoption, published artifacts and deployment verification. Tags, registry publication and successful remote CI each require their own observed result. Framework tests alone do not close a complete banking or insurance journey.
